# ADR-0100: セッションの引き継ぎを /handoff にまとめ、置き場の無いものだけを memory に書く

## 背景

再開の手順は /resume のスキルにあり、「作業の状態は issue と計画に置く（memory の引き継ぎファイルには書かない）」と
書いていた（#45。2026-10-21 の xlc のセッションで、担当、次の順序、未決の判断を memory に手で書いて渡していたのを、
issue と計画に寄せた）。渡す側の手順は無かった。

2026-11-19、claude-harness のセッション（7633dbf6）は /clear の前に、スキルの文に反して memory に
`handoff-2026-11-19.md` を書いた。次のセッションはそれを読んで再開できた。書かれていたもののうち、issue、計画、PR に
置き場が無かったのは次の 4 種類。

- 動いている担当（サブエージェント）と、頼んだ内容。担当は /clear の後も動き続け、報告は次のセッションに届いた
- ユーザーへの質問で、答えを待っているもの
- 別のセッション（xlc-e5）との約束（マージの許可、配備の後の連絡）
- 3 本の作業の次の順序と、それぞれの段階（レビューの何周目か）

同じファイルには、PR の未対応のレビューの指摘 7 件（PR のコメントに書ける）と、次も効く教訓 2 件（memory の feedback に
書ける）も入っていた。

スキルの名前 `resume` は、Claude Code の標準のコマンド `/resume`（前の会話を開き直す）と同じで、どちらを指すかが
紛れる（ユーザー 2026-11-19）。

## 検討した案

1. 1 本のスキル `handoff` に渡す側と受ける側をまとめ、置き場の無いものだけを memory に書く
2. 1 本のスキル `handoff` にまとめ、memory には書かず、セッションに属するものも issue に書く
3. 渡す側と受ける側を 2 本のスキルに分ける（置き場は 1 と同じ）

## 決定と理由

案 1 を採る（ユーザー 2026-11-19 は、memory に書かないという前の文にこだわらず、やりやすい形でよいと答えた）。

- スキル `resume` を `handoff` に改名し、「渡す」と「受ける」の 2 つの節を置く。状態を集めるスクリプトの名前
  （`resume-state`）は変えない（再開時に集めるという役割は同じで、名前が紛れるのはスキルの方だけ）
- 渡すときは、トピックに属するもの（未対応のレビューの指摘、次にやること、前提、未決の判断、試して捨てた方式、教訓）を
  先に本来の場所（PR のコメント、issue、計画、ADR、memory の feedback）へ書く。スクリプトで集め直せるものは書かない。
  残りの、セッションに属するもの（進行中の作業の段階と書いた先、作業の間の順序、動いている担当、ユーザーへの質問の待ち、別のセッションとの
  約束、書く先の無かったユーザーの指示）だけを、memory の `handoff-<YYYY-MM-DD>.md` に書き、`MEMORY.md` に 1 行足す。
  既にある引き継ぎは、自分が受けたか書いたものなら新しいファイルに移して 1 つに保ち、別のセッションのものには触れない
- 受けるときは、スクリプトの出力を読み、`MEMORY.md` に引き継ぎの行があればそのファイルと、それが指す issue、計画、PR の
  コメントを読む。食い違えば出力を採る。引き継ぎが進行中として挙げたブランチは、コミットの `Claude-Session:` が前の
  セッションでも引き受けて続ける（グローバルの CLAUDE.md の、自分のセッションでないブランチを引き受けない規則は、
  渡された作業には当てないので、CLAUDE.md のその項から /handoff を指す。動いている担当のブランチは、担当が止まっていると
  確かめるまで触らない）。済んだ項目は消し、全部が済んだらファイルと行を消す

理由:

- memory の `MEMORY.md` は次のセッションが自動で読むので、スキルを呼び忘れても引き継ぎに気付く。issue に書く案 2 では、
  呼ばなければ読まれない
- セッションに属するものは、どのトピックの issue にも合わない。案 2 では、トピックでない issue が増え、別のセッションとの
  約束が公開のリポジトリの issue に載る
- トピックのものを memory に書かせないので、#45 の狙い（状態を issue と計画に置き、ほかのセッションからも見える）は残る
- 案 3 は、書く形（渡す）と読む形（受ける）が 2 つのファイルに分かれて食い違いうる。常に文脈に載るスキルの description も
  1 つ増える。呼ぶたびに読む本文は半分で済むが、本文は 2 つの節を合わせて 60 行ほどで、差は小さい

### 帰結

- 引き継ぎのファイルの中身（置き場の無いものだけか、項目がそろっているか）は、機械では確かめない。スキルの文と、
  受ける側の「失われたものとしてユーザーに聞く」で補う
- 引き継ぎのファイルは、プロジェクトごとの memory のディレクトリに置くので、同じリポジトリの複数のセッションのものが
  並びうる。名前の末尾の番号で分け、複数あるときは、受ける側がどれを受けるかをユーザーに確かめる
- 状態を集めるスクリプトは GitHub の issue を読まない（docs/issues だけ）。GitHub の issue に書いた次にやることは、
  引き継ぎが番号で指して渡す
- グローバルの CLAUDE.md の Compact Instructions は変えていない（#45 の 3 つ目の項目。compact の要約に残すものと、
  このスキルが集めるものの重なりは、#45 に残す）

### 確認

- `claude/tests/scripts/resume-state.sh` が、改名した後のパス（`skills/handoff/scripts/resume-state.sh`）でスクリプトを
  呼ぶ
- 配備の後、`~/.claude/skills/resume` が消え、`~/.claude/skills/handoff` があることを確かめる（`claude-setup sync` は、
  前の一覧にあってソースから消えたファイルを消す）
