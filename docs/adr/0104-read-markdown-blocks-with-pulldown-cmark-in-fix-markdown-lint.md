# ADR-0104: fix-markdown-lint は Markdown のブロックの構造を pulldown-cmark で読み、表の揃え直しとフェンスの言語の付け足しをその範囲だけに当てる

## 背景

fix-markdown-lint（`crates/fix-markdown-lint/`。ADR-0088 でライブラリの crate にした）は、markdownlint --fix の直せない
MD060（表の桁）と MD040（コードの塊の言語）を直す。呼ぶのは `claude-hooks script fix-markdown-lint`、git hook の
staged-checks、history-rewrite の `realign_tables`（直した行を含む表だけを揃え直す）。

どの行が表でどの行がフェンスかは、手で書いた規則で決めていた（main 5aac2d1f）。

- `fence_open` と `fence_end`: CommonMark のフェンスの開きと閉じ（文字、本数、字下げ）
- `is_indented_code`: 4 桁以上の字下げの行から、字下げの浅い行を前へたどり、最初に見つけた行がリストの項の印なら項の
  中身、字下げの無い行ならコードと見る

`is_indented_code` は項の中身の桁（印の幅と印の後ろの空白）を数えないので、`1. item` の下に 8 桁で字下げしたコード
ブロックの表の形の行を、表として揃え直す（#347）。history-rewrite も同じ関数を行ごとに呼ぶ。

このブランチ（#347 の fix/markdown-lint-list-code-block）で、項の中身の桁を CommonMark の規則で数える形に直し始め、ローカルの
レビューを 3 周回した（#347 のコメント、2026-11-20）。周ごとに、段落とその続き（遅延継続行）の取り違えが別の形で出た。
項の中身の桁を正しく数えるには、段落を区切るほかのブロック（表、HTML のブロック、見出しなど）の規則も手で書くことになる。

関わる事実:

- pulldown-cmark（Rust の CommonMark と GFM のパーサー）は、ja-terms（ADR-0085）と design-records（ADR-0092）が
  `version = "0.13", default-features = false` で使っている。lock の版は 0.13.6（2026-11-20、各 crate の Cargo.lock）
- markdownlint 0.50.0 は micromark で読む。GitHub の描画は cmark-gfm（GFM の参照実装）で読む
- staged-checks は、fix-markdown-lint の前に markdownlint --fix を流す（`crates/claude-hooks/src/staged_checks.rs`）。
  --fix は MD058 と MD031 で、表とフェンスの前後に空の行を足す

## 決定の要因

- コードブロック（字下げしたものとフェンス）の中身を書き換えないこと。表を揃え損ねても文書は壊れないが、コードの中身を
  書き換えると壊れる
- 今の main が正しく書き換える入力（表の揃え直し、言語の無いフェンスへの言語の付け足し）を保つこと
- Markdown のブロックの規則を手で書いて保守しないこと。依存は ADR-0047 の数え方に従う
- fix_markdown と history-rewrite が、同じ判定を 1 度のたどりで使うこと（#399。行ごとに文書を先頭からたどる形は、
  入れ子の項のフェンスが並ぶ 20000 行の文書で 13 秒かかった）

## 検討した案

- 案 A: pulldown-cmark でブロックの構造を読み、GFM の表の範囲と、言語の無いフェンスの開きの行を取る。その範囲だけを
  揃え、その行だけに言語を付ける
- 案 B: 手書きの版（ブランチの 49589ef9）で、3 周目の指摘（下の方式 5）を直して続ける
- 案 C: 遅延継続行を数えず、項の中のフェンスの開きは main と同じく前へたどって受け入れる。表の判定だけを項の中身の桁で
  行う、狭い版にする

試して捨てた方式（#347 のブランチ、2026-11-20。どの版も、そのときのテストとチェックは通った）:

1. 前へたどる判定（main の `is_indented_code`）: 項の中身の桁を数えないので、`1. item` の下に 8 桁で字下げしたコードを
   表として揃える（#347 の再現）。前の行の並びで決まる遅延継続行とフェンスの範囲を扱えない
2. 遅延継続行で項を閉じる版（88830a45）: 項の中身の桁を浅く見る側に倒せば、表を揃え損ねるだけで済むと考えた。反例:
   `1. item\n  continued\n\n    ```\n   | a | b |…\n    ```` では、項の中のフェンスを字下げしたコードと見て、フェンスの
   中身の表を揃える。フェンスの開きの判定では、桁を浅く見ることは書き換えない側に倒れない（レビュー 1 周目）
3. 呼ぶたびに先頭からたどる版（e962623b の前の形）: `is_indented_code` と `fence_open` を呼ぶたびに文書を先頭から
   たどる。入れ子の項のフェンスが並ぶ 20000 行の文書で 13 秒、2000 行で 0.14 秒かかった（リリースのビルド）
4. 項の桁を数えるたどりとフェンスの範囲を別々に決める版（e962623b）: `fence_end` は閉じのフェンスだけを見て、たどりの
   方は項を閉じる字下げの浅い行でもフェンスを閉じた。両者が食い違い、項を閉じた後の表を揃えた（レビュー 2 周目）
5. 1 度のたどり（`Blocks::read`）が項の桁とフェンスの範囲の両方を決める版（49589ef9）: 表の行を段落と見て、表の次の
   字下げの浅い行を遅延継続行と見る（例: 2 桁の字下げの `- inner` の項の中の表の次に字下げの無い `text` の行、空の行、
   6 桁の字下げの表の形の行が続くと、項の外の 6 桁のコードを揃える）。HTML のブロック（`<div>`）が段落を区切らない。
   全角の空白を外してから `#` を見るので、空白と全角の空白の後ろの `# x` を見出しと見て項を閉じる。レビューの担当が pulldown-cmark 0.13.6 と 300000 個のランダムな入力で
   比べ、41 個で、main は書き換えず、この版だけがコードを書き換えた（レビュー 3 周目）

ブランチの上の 49589ef9 までのコミットは、案 A の実装で置き換え、履歴に残していない（コミットの hash は #347 の
コメントの時点のもの）。

## 決定と理由

採用: 案 A。

- 読み方: `pulldown_cmark::Parser::new_ext(content, Options::ENABLE_TABLES)` の offset で、`Tag::Table` の範囲と、
  info string が空の `CodeBlockKind::Fenced` の開きの行を取る。版と feature は ja-terms と design-records と同じ
  （`version = "0.13", default-features = false`）
- 表: 見出しの行が表の行（両端の空白を外すと `|` で始まって `|` で終わる）で、次の行が区切りの行のものを揃える。範囲は
  見出しの行から、表の範囲の中で、見出しと同じ字下げ（空白とタブ）の表の行が続くところまで。GFM が表に数える `|` の
  無い行と、字下げの違う行は揃えない。`format_table` は見出しの字下げを全部の行に付け直すので、字下げの違う行を揃えると
  行がリストの項の中や外に動く。また、pulldown-cmark が表の行に読む深い字下げの行を、cmark-gfm は字下げしたコード
  ブロックに読む
- フェンス: 言語の無い開きの行の末尾に、pulldown-cmark が読んだ中身（コンテナの字下げを外したもの）から推定した言語を
  付ける。開きの行の頭が引用の `>` やリストの印でも付ける（info string が空なので、行の末尾はフェンスの文字で終わる）
- ほかの行は書き換えない。字下げしたコードブロック、フェンスの中身、HTML のブロックの中の表の形の行は、表の範囲に
  入らない
- ライブラリの `tables(content)` が表の行の範囲を返し、history-rewrite の `realign_tables` はそれを 1 度呼んで、直した
  行を含む範囲だけを揃える。`fence_open`、`fence_end`、`is_indented_code` は消す（#399）

理由:

- 案 A は、CommonMark と GFM のブロックの規則を手で書かない。方式 2〜5 の取り違えは、どれもブロックの規則の一部を
  手で書いたことに由来する。案 B は、比べるたびに残りが見つかり続ける見込み（3 周で毎回別の形が出た）
- 案 C は、遅延継続行の後の形（方式 2 の反例）が直らずに残り、フェンスと表で項の判定が 2 つに分かれる
- pulldown-cmark は Rust の CommonMark のパーサーとして事実上の標準で（ADR-0085）、このリポジトリで既に使っている。
  ADR-0047 の数え方で、手で書く規則より保守の費用が小さい
- fix_markdown と history-rewrite が同じ `tables` を使い、どちらも文書を 1 度だけ読む

### 帰結

- 良い点: 項の中のコードブロックとフェンスの中身、HTML のブロックの中を書き換えない。main はランダムな入力 300000 個
  （下の確認）のうち、15404 個でコードの中身を、16566 個で HTML のブロックの中を書き換えていた
- 良い点: 引用の中のフェンスと、リストの印と同じ行のフェンスにも言語を付ける。main は付けなかった
- 悪い点: pulldown-cmark、cmark-gfm、micromark は、空の行で区切らないブロックの並び（表の直後の字下げした行やリストの
  印など）で読み方が違うことがある。そこで main と結果が変わる（下の確認）。staged-checks は markdownlint --fix で表と
  フェンスの前後に空の行を足してから直すので、ふつうの文書ではこの違いに当たりにくい
- 悪い点: main が書き換えていた次の入力を書き換えない
  - 行頭に全角の空白があり、その後ろが表の形の行。全角の空白は字下げでなくセルの中身で、見出しのセル（3 つ）が
    区切りの行（2 つ）と合わず、GFM の表でない。main は全角の空白を外して表にしていた
  - 閉じのフェンスの後ろに \x1c〜\x1f のある行（`` ```\x1c ``）の後ろの表の形の行。CommonMark は閉じに数えないので、
    フェンスの中身。main は Python の `str.isspace` に合わせて閉じに数えていた（ADR-0087）
  - 字下げの違う行の続く表は、見出しと同じ字下げの行まで揃える（main は表の形の行の続く限り、見出しの字下げで揃えた）。
    全角の空白で始まる本体の行でも表を止める（全角の空白はセルの中身で、外して揃えるとセルが変わる）
- 言語の推定は、コンテナの字下げを外した中身を見るので、リストの項の中のフェンスで main と違う言語を付けることがある
  （`^def` などの行頭の形が当たる）

### 確認

- テスト: `crates/fix-markdown-lint/tests/list_items.rs`（番号つきと番号なしの項、入れ子の項、遅延継続行の後、表の
  行の後、HTML のブロックの後のコードブロックとフェンスの中身を書き換えず、項の中のコードでない表を揃える）、
  `tests/code_blocks.rs`（リストの外の表とコードブロック）、history-rewrite の `tests/transform.rs`（項の中のコード
  ブロックと、`\r\n` の文書の印だけの行）
- main（5aac2d1f）と新しい版の比較（2026-11-20、ブランチの 08f4763f。ba94aa03 で再実行して同じ数。比べたツールと結果は #347 のコメント）:
  - このリポジトリの追跡している Markdown 127 個、`~/.claude` の Markdown 543 個、ほか 28 個: 結果の違うのは 3 個で、
    どれも新しい版の側が cmark-gfm と同じ読み方（`<dir>` で始まる HTML のブロックの中を main が書き換えた、引用の中の
    フェンスに言語を付けた、項の中のフェンスに推定した言語が違う）。表の行の空白を詰め、フェンスの言語を外して崩した
    版では、違うのは 10 個で、同じ形と言語の推定の違いだけ
  - ランダムな入力（方式 5 のレビューで比べた部品に 7 つを足し、2〜9 個並べたもの）300000 個を 2 組（種 1 と 7）: 新しい版が
    書き換えた行は、どれも pulldown-cmark の表の範囲の中か、言語の無いフェンスの開きの行だった。main は書き換えないのに
    新しい版がコードブロック（pulldown-cmark の読み方）の中身を書き換えた入力は 0 個
  - cmark-gfm 0.29.0.gfm.13 との比較（種 1 の入力のうち main と結果の違う入力の 10 個に 1 個、9743 個）: 新しい版だけが
    書き換えた行のうち、cmark-gfm がコードブロックの中身に読む行は 1 行（表の直後の `-` の行を、pulldown-cmark は
    リストの項の開きに、cmark-gfm は表の行に読み、その後の `` ``` `` を pulldown-cmark は開きに、cmark-gfm は閉じに読む）。
    main だけが書き換えた行のうち、cmark-gfm がコードブロックの中身に読む行は 4817 行、HTML のブロックの中は 3158 行
  - markdownlint 0.50.0 との比較（同じ 9743 個、MD040）: 新しい版だけが言語を付けた行 4930 行のうち、markdownlint が
    言語の無いフェンスの開きと見ないのは 15 行
- Windows の CI（`windows.yml`）で、fix-markdown-lint、history-rewrite、claude-hooks のテストが通る
