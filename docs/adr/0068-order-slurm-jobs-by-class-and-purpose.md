# ADR-0068: Slurm のジョブに区分と目的を必須にし、待ち行列の順を区分で決めて、依頼の計算の本数の上限をやめる

## 背景

/delegate は、頼む側に「実機の試験や計算には、回数の上限を完成の形に書く」、受ける側の「作業中の規則」に「実機の試験や
計算は、完成の形にある回数の上限を超えそうなら止まって報告する」と書いていた（2026-10-14 の 7cad235f で足し、ADR は無い）。
ユーザーの案を渡すときも、測らないと決められなければ「測る回数の上限を「完成の形」に」添える（ADR-0055 の案 A）。
上限で守ろうとしていたのは、投げる前に見積もらせることと、見込みの外れた方式で流し続ける損を限ることである。

待ち行列（`squeue`）に出るのは、名前、見積もり、開始の見込み、連絡先（ブランチ、投げた場所、セッション）だけで
（ADR-0007、ADR-0030）、そのジョブの結果が何を決めるか、記録に載せる本番か検討かは出ない。どのジョブを先に流すべきかを
待ち行列から確かめられないので、本数の上限がその代わりになっていた。

2026-10-29 に、xlc の #0200 の担当（ブランチ fix/0200-step-instability-after-power-change）が、排他でない 4 本を流した
（Slurm 599〜602。`sacct -j 599,600,601,602 -X -o JobID,JobName,State,Elapsed,SubmitLine`）。599 は FAILED（1 時間
16 分 47 秒）、600〜602 は COMPLETED（2 時間 28 分 20 秒、2 時間 29 分 9 秒、2 時間 27 分 54 秒）で、Elapsed の和は 8 時間
42 分 10 秒だった。依頼は完成の形に「Slurm は 2 本まで」と書いていた（親のセッションの依頼文の 9 行目）。親のセッションに
よれば、担当はそれを「同時に 2 本」と読み、完了した 3 本のうち 1 本は途中で目標を変えたために使わなかった（担当の記録は
確かめていない）。上限は、守ったかの判定が読み方で変わり、
見積もりを書かせることも、外れた方式の損を限ることも果たさなかった。

ユーザーは 2026-10-29 に次のように問うた。「何でSlurmの上限を絞っているんですか？」（ユーザー 2026-10-29）、
「優先順位を客観的に確認できれば良いのでは？」（ユーザー 2026-10-29）。どの案を採るかは親のセッションが決めた。

## 決定の要因

- 待っているジョブのどれを先に流すべきかを、待ち行列だけで、誰が見ても同じに確かめられること
- 投げる前に見積もりを書かせ、見込みの外れた方式で再実行するときに理由が残ること
- 親のセッションの返事を待つ仕組みにしないこと（担当は親の返事を待たずに進める）
- 今の優先度の仕組み（ADR-0030 の `scontrol top`、ADR-0053 のパーティション timed）の上に足すこと

## 検討した案

- 案 A: 依頼の完成の形に本数の上限を書く（今）
- 案 B（採用）: ジョブに区分と目的を必須にし、待ち行列の順を区分で決める。依頼には目的と区分を書き、担当は見積もりと
  再実行の理由を報告に書く。本数の上限は待ち行列が混むときだけ
- 案 C: 担当が投げるジョブを、親のセッションがすべて承認する
- 案 D: 区分を Slurm の優先度で表す。区分ごとに `--nice` を付け（record 0、decision N、trial 2N。N は `PriorityWeightAge`
  の上限より大きくし、`PriorityWeightPartition` も合わせる）、Slurm に区分の順を保たせる

## 決定と理由

採用: 「案 B」。区分と目的が待ち行列に見えれば、どのジョブを先に流すかは区分の順で決まり、本数で絞る理由が無くなる。
見積もりと再実行の理由は、上限の代わりに担当の報告に残す。

- `slurm-run.sh` は `--class <区分>`、`--ref <参照>`、`--purpose <目的>` を必須にし、どれかが無いか形が違えば投げずに
  エラーで止まる
  - 区分は `timed`（時間を記録する測定）、`record`（記録に載せる本番）、`decision`（決定に要る確認）、`trial`（検討）の 4 つで、
    この順に優先する。時間の記録はほかの計算を止めて走る（ADR-0053）ので最上位、記録に載せる本番は結論の数値になるので
    決定の確認より上、検討は結論を変えないので最下位にする
  - 区分 `timed` は、`--timed` を付けなくてもパーティション timed に投げる（時間を記録する測定は timed でしか記録に使えない）。
    `--timed` は数分の急ぐ計算にも使う（ADR-0053）ので残し、ほかの区分に付けたときは区分をそのままにして timed に投げる。
    区分 `timed` と `-c` は、`--timed` と `-c` と同じく組めない
  - 参照は issue か ADR の番号（`#NNNN`、`ADR-NNNN`、カンマで複数）で、無いときは `- <理由>` と書く。目的は結果が何を
    決めるかの 1 文
  - 3 つはジョブのコメントの先頭に `<区分> | <参照> | <目的> | <連絡先>` の形で入れ、`squeue` の `%k` に出す。参照と目的には
    改行と `|` を許さず、区切りを壊さない。終わったときの `TIME:` 行の末尾にも `class= ref= purpose=` を出し、ログに残す
- 一覧のスクリプト `slurm-queue.sh` が、コメントを分けて、ジョブを走る順（パーティション timed、main の順。その中は走って
  いるもの、止められたもの、待っているものの優先度の順）に、番号、状態、パーティション、優先度、区分、見積もり、開始の見込み、
  名前、参照、目的、連絡先で並べる。`--order [--first <番号>]` は、パーティション main の区分のある動かせる待っているジョブを、
  区分の順（同じ区分は今の順、`--first` のジョブは自分の区分の先頭）に並べた番号の列を、今の順と違うか、区分の無い待っているジョブが列のジョブより前にいるときだけ出す（列を渡すと区分の無い
  ジョブは後ろに回る）。動かせない
  ジョブ（優先度が 1 以下の保留と配列の親ジョブ。`scontrol top` が受け付けない）は列に入れず、一覧に「動かせない」と出す
- `slurm-run.sh` は、main に投げたジョブの番号を得た直後に `slurm-queue.sh --order`（`--top` なら `--first <自分>`）を呼び、
  列があれば `scontrol top <列>`（ADR-0030）に渡す。`scontrol top` は走り始めたジョブや取り消したジョブを含む列を拒まない
  （終了コード 0。存在しない番号だけ拒む。r995 で 2026-10-30 に確かめた。下の「確認」）ので、成功の後も読み直して区分の順に
  なったことを確かめ、並べ直しが要らなくなるまで繰り返す（同時に投げたほかの `slurm-run.sh` の列が後から通って上書きした
  ときも直る。上限 3 回で、超えたら警告して投げた順に任せる）。並べ方は `slurm-queue.sh` の 1 か所にあり、区分の順は投げるたびに
  投げたセッションが保つ（各セッションの手作業に頼らない。`slurm-run.sh` はグローバルの許可にあるので、`scontrol top` の許可も
  要らない）。`scontrol top` は渡したジョブをその順に先頭へ出すので、1 つの列で渡す（ジョブごとに分けると最後に出したジョブが
  先頭になり、1 本だけ出すとその前にいた上の区分のジョブも追い越す）。`--top` は自分の区分の先頭に出し、上の区分のジョブは
  追い越さない
- パーティション timed は区分で並べず、ADR-0053 のとおり投げた順に走る（`--top` のときだけ投げたジョブを先頭に出す）。
  timed のジョブは時間の記録と、走っているジョブの終わりを待てない数分の計算で、区分で並べると急ぐ計算が長い測定の後ろに回る
- `slurm-run.sh` の外で順が崩れたとき（区分の無いジョブ、手で実行した `scontrol top`）は、一覧が `ORDER: main:` の行で、
  並べ直す `scontrol top <列>` を示す（投げたセッションによらず実行してよい。並べ直すだけで、取り消さない）
- 順序の規則（/slurm-run）: main は区分の順に流す。走っているジョブは止めない（区分の順は待っているジョブの順だけを決める）。
  本数の上限は置かない
- /delegate: 頼む側は、計算の目的と区分を完成の形に書く（ADR-0055 の測る案も同じ。ADR-0055 の「## 変更」に書く）。担当は、投げる前に 1 本の見積もりと合計の時間を出して報告に書き、
  失敗や方針の変更で再実行するときは理由を報告に書く。本数の上限は、待ち行列が混む（ほかのセッションのジョブが待っている）
  ときだけ書く

案 A を採らない理由: 背景のとおり、上限は読み方で守ったかが変わり、見積もりも損の上限も残さなかった。上限を厳しく書く
ほど、決定に要る確認まで流せなくなる。

案 C を採らない理由: 担当は親の返事を待たずに進める作りで（/delegate の「報告は途中で止まらず、最後に 1 度だけ返す」）、
承認を挟むと担当が止まる。親が会話を圧縮している間や別の担当を見ている間は承認が遅れ、待ち行列が空いたまま進まない。

案 D を採らない理由: 並べ直しの列、読み直しの繰り返し、同時に投げたときの競合がすべて要らなくなる利点はあるが、slurm.conf の
重みの変更と r995 の rebuild が要る。`--nice` は非特権では優先度を下げる方向にしか付けられないので、`--top`（区分の中で前へ）を
優先度で表せない。パーティション timed は区分で並べない例外で、それと組み合わせる設計も別に要る。後で見直す候補として #534 に
書く。

### 帰結

- 良い点: 投げるたびに main が区分の順に並び、`slurm-queue.sh` の 1 回の実行で、各ジョブの区分と目的と、外で崩れたときの
  並べ替えのコマンドが分かる。ログの `TIME:` 行に
  目的が残るので、後から時間を読むときに何のジョブかが分かる
- 悪い点: 投げるたびに区分と目的を書く手間が増える。目的の文の中身は機械で確かめられず、`trial` と書くべきジョブに `record`
  と書けば上に並ぶ（区分の誤りは連絡先のブランチと報告で親が読む）
- 悪い点: 列に入らないジョブ（区分の無いジョブ、動かせないジョブ）は、並べ直すたびに列のジョブの後ろに回る（ADR-0030 の
  `scontrol top` の性質）。区分を必須にする前に投げたジョブと `ALLOW_RAW_SBATCH` のジョブが当たる
- 悪い点: 投げるたびに、ほかのセッションの待っているジョブの nice も変わる（並べ直す列に入るため）
- 急ぐ計算: `--top` は main では同じ区分の中で前に出す。走っているジョブの終わりを待てない数分の計算は、区分を変えずに `--timed` で
  投げる（ADR-0053 のまま）。区分の順を越えて 1 本を先に出す仕組みは作らない（親のセッションの判断。2026-10-30）
- 悪い点: 区分の順は main の中の順だけを決める。`--timed` を付けた下の区分の急ぐ計算は、走っている上の区分の
  `main` のジョブを止めて走る（ADR-0053 のまま。`--timed` を数分の計算に限る規則は文書にあり、スクリプトは確かめない）
- 悪い点: r995 の Slurm は `AccountingStoreFlags` を設定しておらず（2026-10-30 の `scontrol show config` で `(null)`）、
  `sacct` はコメントを持たない。終わったジョブの目的は `TIME:` 行とログでしか読めない
- 古い形の呼び出しのうち、nixfiles の分（`.claude/CLAUDE.md`、guard-sbatch の拒否の文言、`modules/slurm/common.nix` の
  コメント）はこのブランチで直した。xlc の CLAUDE.md とスキル（openmc-reference、verification-record）、docs/environment.md、
  ADR-0196 は xlc の別のブランチで合わせる（#534）

### 確認

- `.claude/tests/scripts/slurm-run.sh`: 区分、参照、目的のどれかが無いか形が違えば投げずにエラー、コメントの先頭の形、
  `TIME:` 行の `class= ref= purpose=`、区分 `timed` のパーティション、区分 `timed` と `-c` のエラー、投げた後の並べ直し
  （main の区分の順、`--top` で自分の区分の先頭、timed は並べ直さない、待ち行列を読めないときの警告）
- `.claude/tests/scripts/slurm-queue.sh`: 走る順の並び、コメントの分け方（連絡先の `|`、区分の無いジョブ）、`ORDER:` の
  行を出す条件と出さない条件、timed を並べないこと、動かせないジョブ、`--order` と `--first` の列
- 2026-10-30 に、このブランチの `slurm-run.sh` で r995 に `-c 2` の 30 秒のジョブ（Slurm 603）を投げ、`squeue` の COMMENT、
  `slurm-queue.sh` の出力、`TIME:` 行に区分、参照、目的が出ることを確かめた
- 2026-10-30 02:19〜02:22 JST に、r995 で `scontrol top` の列の扱いを確かめた。待ち行列が空のときに、このブランチの
  `slurm-run.sh` で区分 trial、排他の `sleep 90` を a、b、c の順に投げた（Slurm 604、605、606。3 本とも優先度 10000）。
  604 が走り、605 と 606 が待つ状態で次を実行した（順は `squeue --format '%i|%j|%T|%Q|%y' --sort=-p,i`。%y は nice）
  - `scontrol top 606,605` は終了コード 0 で出力なし。後の順は列の順（c、b）になった:

    ```text
    604|top-check-a|RUNNING|10000|0
    606|top-check-c|PENDING|10000|0
    605|top-check-b|PENDING|9999|1
    ```

  - `scancel 606` の後の `scontrol top 606,605`（取り消したジョブを含む列）は終了コード 0 で出力なし。拒まれなかった
  - 走っている 604 を含む `scontrol top 604,605` も終了コード 0 で出力なし。拒まれなかった
  - 存在しない番号を含む `scontrol top 999999,605` は終了コード 1 で、`Invalid job id specified for job 999999,605` と出た
  - 走り始めたジョブや取り消したジョブを含む列で、残りのジョブが動くかは、待っているジョブが 1 本だけだったので見分けて
    いない。読み直しの繰り返しは、読み直した順が区分の順になるまで続けるので、部分的に動くかによらない
