# Handoff

セッションをまたいで作業を続けるための、渡す側と受ける側の手順。作業の状態は、まず issue、計画（docs/plans）、PR に置く。
そこに置き場の無い、セッションに属するものだけを memory の引き継ぎのファイルに書く（トピックのものを memory に置くと、
issue や PR と食い違ったまま残り、ほかのセッションからも見えない）。

## 現在の状態

!`~/.claude/skills/handoff/scripts/resume-state.sh`

## 渡す

/clear の前、セッションの終わり、長く離れる前に行う。

1. 上の出力で分かる状態（worktree の一覧、未コミットの変更、開いている PR の一覧、Slurm のジョブ、docs/issues の issue）は
   書き直さない（次のセッションが同じスクリプトで集め直す）。ブランチと PR の番号は、下の 4 で作業を指す名前としてだけ書く
2. トピックに属するものを、先に本来の場所へ書く
   - 未対応のレビューの指摘: PR のコメント（PR が無ければ issue）
   - 次にやること、前提、未決の判断: issue か計画
   - 試して捨てた方式と、その理由: ADR か issue
   - 次の作業にも効く教訓: memory（feedback）か /retro
3. memory に引き継ぎのファイル（`handoff-`）が既にあれば、書く前に読む。自分が受けたか書いたものなら、残っている項目を
   4 で書くファイルに移し、古いファイルと `MEMORY.md` の行を消す（引き継ぎを 1 つに保つ）。別のセッションが書いたものには
   触れず、自分のファイルの名前の末尾に `-2` のように番号を付けて分ける
4. 残りを memory の `handoff-<YYYY-MM-DD>.md`（`type: project`）に書き、`MEMORY.md` に 1 行足す（次のセッションは
   `MEMORY.md` を自動で読むので、スキルを呼ばなくても気付く）。書くもの:
   - 進行中の作業ごとに、ブランチ、PR、どの段階か（チェック、レビューの何周目、マージ、配備）と、2 で書いた先（issue や
     PR のコメントの番号）。次にやることは書いた先に置き、ここからは指すだけにする
   - 作業の間の順序と優先（計画に書いてあれば、計画を指す）
   - 動いている担当（サブエージェント）: 何を頼んだか、ブランチ、依頼文のパス、報告が届かないときにどうするか
   - ユーザーへの質問で、答えを待っているもの
   - 別のセッションとの約束（何を、いつ知らせるか）
   - ユーザーが会話中に出した指示と決定のうち、2 で書く先が無かったもの
5. 書いたファイルを読み直し、この会話を知らない読み手が最初の 1 手を打てるかを確かめる（hash、PR の番号、絶対パスで
   書く。会話の中だけで通じる呼び名は書かない）。`~/.claude/bin/ja-terms check <ファイル>` で語も確かめる（次のセッションが
   この文をコミットや依頼にコピーする）
6. ユーザーに、書いたファイルと、次のセッションで /handoff を呼べば続けられることを伝える

## 受ける

セッションの開始、compact の後、/clear の後に行う。

1. 上の出力を読み、`NEXT:` の行に従う
2. `MEMORY.md` に引き継ぎ（`handoff-`）の行があれば、そのファイルと、それが指す issue、計画、PR のコメントを読む。
   書かれた状態は書いた時点のもので、上の出力と食い違えば、出力（今の事実）を採る。引き継ぎが複数あれば（同じ
   リポジトリの別のセッションのものが並びうる）、どれを受けるかをユーザーに確かめる
3. `session=` が自分のセッションでない worktree とブランチは、担当が別なので触らない（引き受けず、担当かユーザーに回す）。
   ただし、受けた引き継ぎが進行中の作業として挙げたブランチは、渡したセッションから引き受けたものとして続ける
   （セッションを閉じて渡すと、`session=` は前のセッションのまま残る）。動いている担当のブランチは、4 で担当が止まって
   いると確かめるまで触らない
4. 引き継ぎに動いている担当があれば、今も動いているかを確かめる（ListAgents があればそれで）。/clear の後は、担当は
   動き続け、報告はこのセッションに届くので、報告を待つ。動いていなければ（セッションを閉じると止まる）、ブランチの
   コミットと PR を見て続きを決める
5. `docs/plans/` があれば、「進め方」の次の項目を読む
6. Slurm のジョブがあれば `~/.claude/scripts/slurm-queue.sh` で待ち行列を見る。AWS の監視などプロジェクト固有の状態は、
   そのリポジトリの README か計画に従って集める
7. 次にやること、前提、未決の判断が issue にも計画にも書かれていなければ（compact の要約にだけある、渡さずに終わった
   セッションの続きなど）、先にそこへ書く
8. 集めた状態をユーザーに 3〜5 行で報告し、次の 1 手を示す
9. 引き継ぎの項目は、済んだら消す。全部が済んだら、ファイルと `MEMORY.md` の行を消す（古い引き継ぎが残ると、次の
   セッションが済んだ作業をやり直す）

## 判断

- 次の順序と優先は、計画、issue、引き継ぎから読む（スクリプトの収集で分かるのは事実だけ）
- 出力に無いもの（実行中の担当、未決の判断）が issue にも計画にも引き継ぎにも書かれていなければ、失われたものとして
  ユーザーに聞く
